# keel 交付流程开发契约与验证依据

版本：1.0-review · 日期：2026-10-26 · 读者：专业开发人员，不要求熟悉机房实施。

**交付目的：** 让开发团队可以回答“什么时候允许执行、执行到什么程度算完成、必须留下什么产物、谁可以使用它、变更或失败后怎样恢复”，并据此设计接口、编排和验收。流程图是这些契约的视图，不是完整规格的替代物。

**唯一需求输入：** 本次附件 `keel-delivery-fishbone.md`（SHA-256见校验报告）。原附件所引用的PRD条款在此沿用为追溯线索，本次没有把未重新核对的外部文件当作新增需求来源。

**四种语义标签贯穿本文：**

- **K｜已知要求：** 附件明确规定，须保持。
- **D｜推导约束：** 为使已知要求同时成立所必需的逻辑约束，附推导依据；可由评审反驳，不能伪装成原文。
- **P｜实现建议：** 本次给出的数据组织、事务边界、错误表达或验证方法。研发可采用等价实现；这类常规工程选择不要求全部转交业务审批。
- **Q｜业务待决策：** 阈值、适用范围、采样覆盖、豁免等影响验收语义的缺口。提供决策责任与开发边界，不用代码默认值悄悄补完。

本文不声明“所有顶尖专家都会同意”，而采用资深团队能进行明确评审的标准：**术语可对应对象，条件可执行，结果可追溯，失败可恢复，反例可构造，未决项可定位。**

## 1. 资深专家还会考虑什么

以下是针对本项目的审查问题，不是通用架构名词清单。

| 关注点 | 具体风险／反例 | 对本次文档施加的约束 |
|---|---|---|
| 完成的证明义务 | 一个脚本退出0，但配置未生效；机器显示netverified，但缺新NCCL组路径 | 执行状态、检查结果、证据可消费性分开；每步规定完成证明 |
| 稳定身份与重装／换件 | OS接口名或BDF顺序改变，被当成同一个端口；新硬件继承旧测试通过 | 引用稳定实体及关系版本；观察值不是身份，换件后沿依赖失效 |
| 权威数据源与期望独立性 | 用待验实测拓扑生成期望，验证永远成功；前端和后端各自算门禁 | 期望、观测、确认关系、门禁分别归属；判定在后端，原始证据保留 |
| 启动条件与完成条件 | 为了做G2先要求NP-3，或为修复T7先要求普通G4已通过 | 正常前向依赖无循环；修复例外单独建模，不能以普通准入阻塞修复自身 |
| 检查后的并发变更 | 准入检查刚通过，另一任务已更新ConfigSet；旧任务稍后回写“当前PASS” | 派发与发布时核对同一依赖快照，拒绝过时写成为当前证明；具体CAS为P建议 |
| 断线后的不确定副作用 | 交换机实际已应用配置但回执丢失，重试再次执行；Kill超时被当终止成功 | 结果未知必须对账；幂等键与设备回执配合，恢复不能凭请求超时推断未执行 |
| 资源竞争与测量污染 | G5和NCCL同时占用同一NIC导致吞吐下降；测试自身制造拥塞又被判成固有缺陷 | 测试窗口与互斥纳入准入；观测绑定负载上下文，批次与并发必须可追溯 |
| 时间与质量 | 30s测试拿不到3600s规则窗口；计数重置后差值被当零；30s就绪证明被误当任务超时 | 区分采集时间、规则窗口、动态新鲜度、消费时有效期；缺测和0分开 |
| 覆盖的数学对象 | 服务器数量全覆盖，被误认成所有NIC对、方向和热点路径全覆盖 | 覆盖集合的单位明确，必须从消费任务反推required_path_coverage |
| 变化的影响半径 | 只换一口线却重测全项目；更新规则后仍消费依赖旧规则的新结论 | 失效沿实际依赖传播；保留历史，不全局清零，也不默许旧结论永不过期 |
| 可诊断性与错误归因 | 采集权限错误被判网卡坏；根因定位到交换机后工单source被改写 | 采集质量、检测差异、发现来源和责任域独立表达 |
| 可验证性与误判成本 | “测试都绿了”实际上只验证了作者自己的假设 | 固定来源、独立预期样本、反例／变异检查、现场PoC与角色签署分层提供证据 |

这些问题决定了本项目首先是一个**按版本和范围消费证据的编排系统**。页面上的阶段完成状态，是它的呈现结果。

## 2. 从哪些不同角度入手

### 2.1 从最终放行条件反推，而非从页面顺序往下堆功能

以一次跨机NCCL通信组为起点，反推它需要哪些GPU、NIC、接口、软件与性能基线，再反推需要哪些G5路径和档位证据，再反推G4配置、G3映射、G2端口确认、G1与网络底座事实。由此发现：

- **G5不是机器属性的一个永久布尔值。** 同一份证据可以适用于通信组甲，却不适用于通信组乙。
- **网络底座不是服务器流程前面的全局大锁。** 网络开通、预校验、配置、健康等产物在不同阶段被消费；装机可以并行。
- **G4是明确的契约边界。** G3发布关系，G4把关系转换成配置，G5才验证运行表现。三者不能合成“验机完成”。

### 2.2 从对象所有权和数据生命周期入手

| 数据层 | 表达什么 | 主要权威来源 | 不可替代的下一层 |
|---|---|---|---|
| 期望 | 该有什么设备、连接、配置和性能要求 | BOM、独立型号、商定基线、批准策略 | 不能证明设备实际如此 |
| 观测 | 某对象在某时段实际返回了什么 | 主机／交换机／BMC采集及工具原始输出 | 不能直接等同已确认映射或验收通过 |
| 确认关系 | 哪个物理端口对应哪个OS／PCIe／对端实体 | G2确认与G3 MappingRevision | 不能证明配置已经应用 |
| 应用结果 | 某版本配置是否应用并读回验证 | ConfigSet／PushJob及回执 | 不能证明负载下质量合格 |
| 检测结果 | 对哪个范围、哪个档位判了什么 | G5／NCCL原始结果与规则 | 不能自动适用于以后所有任务 |
| 消费证明 | 当前任务能否使用上述结论 | GateEvidence＋当前依赖／范围／时间核验 | 不是对真实世界的无限期保证 |

物理实体、关系版本和证据实例分别保存；不以“最新一次成功”替代显式引用。

### 2.3 从故障与竞争条件入手

对每个有副作用的流程追问四件事：派发前失联、执行中失联、执行完成但回执丢失、结果已回但关联配置改变时，下一步分别是什么？

**P建议：** 每次尝试维护动作幂等身份和可查询回执；记录“结果未知”时停止盲重放，先查实际状态。只读采集、配置应用、固件刷写、负载测试不能共用一套无差别重试策略。整组NCCL恢复仍遵守原文的GroupAttempt规则。

同时检验“安全性”和“能否推进”：不仅检查错误路径不会放行，还要检查修好之后是否存在合法复验路径。工单未关闭的故障必须能通过限定issue.verify复测，否则系统会卡死在“必须先通过才能验证”。

### 2.4 从独立判定依据反推验收

从每条结论倒推需要什么可核验事实：谁提供期望、哪个独立采集面证明实际、判定用了哪个版本、能构造什么失败反例、修复后需要哪些变化才能恢复。这比堆叠“测试项已执行”更接近验收需要。

## 3. 开发团队可接受的表达方式

### 3.1 使用流程契约，不使用含糊的动作描述

每个流程固定九个字段：**输入及来源、资源、前置断言、执行动作、后置产物、完成证明、失败与阻断、恢复与重试、失效条件**。每个产物都写明后续消费者，详见第5、6节。

表达示例：

| 不足以编码的描述 | 可评审的契约表达 |
|---|---|
| 网络正常后运行NCCL | 本次GroupRun的目标、所需端口路径和档位，均被有效G5证据覆盖；依赖版本一致；NP-5/6复验；资源和软件基线满足 |
| 线序检查通过 | BOM期望与主机LLDP、交换机LLDP按稳定端口对一致；必需证据完整；四步StepReport与最终DL确认可引用 |
| 修完就重跑 | 修复记录绑定工单和受影响对象；issue.verify仅豁免本故障；复验覆盖相应版本且PASS后才提议关闭 |
| 网络测试五层依次执行 | 原文只明确五层检查与先预检；层间严格串行和停止范围仍属Q1，不能直接编码成已批准的五个串行Gate |

### 3.2 三个状态轴分开

**K：** 原文GateEvidence只有 `PASS / FAIL / BLOCKED / WAIVED`。不要为了表示数据质量再添加第五种门禁结论。

| 轴 | 问题 | 示例 |
|---|---|---|
| 执行状态 | 任务是否启动、完成、被终止，副作用是否明确？ | 进程完成但结果未回；断线后结果未知 |
| 检测结果与观测质量 | 是否有证据证明符合或违反判据？ | 测试失败；计数不可得为unknown；近似证据标approximation |
| 当前可消费性 | 对本次目标、版本、档位、路径、时间是否适用？ | 历史PASS保留，但ConfigSet变化导致当前不可用 |

**D：** “历史结论仍为PASS”与“现在不能放行”可以同时成立；这不是矛盾。把它们塞进一个status字段才会导致覆盖历史或永久放行。

### 3.3 可执行的判定逻辑

以下是P建议的评审伪代码，函数名和拒绝原因不是已存在API。档位兼容、路径生成、豁免传播等未定策略不得默认true。

```text
can_consume(evidence, requested_scope, now):
  核对项目
  核对目标集合与所需端口路径覆盖
  核对test_profile适用性与全部相关依赖版本
  核对证据有效期；动态readiness在当前消费/派发时单独刷新
  核对每个必需观测能力、质量和所需窗口
  接受PASS，或本次明确允许且有效的WAIVED
  返回允许/拒绝和逐项缺口；不修改历史evidence结论

publish_gate_result(attempt):
  持久化原始结果和回执
  重新核对本次冻结的相关依赖版本
  若相关前提已改变：保留历史测量，不发布为当前可用证明
  否则：按已确认的规则、覆盖与豁免策略生成GateEvidence
```

**P建议的事务边界：**

1. 接受任务时冻结目标与引用版本，校验权限、申请资源；持久化尝试及待派发事件。
2. 执行器在动作前核验允许的目标、租约／fencing信息和动作身份；重复消息查询已有回执。
3. 结果回收时先保存真实输出；发布当前可用证据时做依赖版本比较。可以用数据库事务／条件更新实现，不必新增微服务。
4. 变更和失效采用反向依赖索引计算影响范围。证据不被物理覆盖，读者通过当前条件判断是否仍可消费。

这是并发正确性的实现建议；原文件未给出完整数据库事务或API规格，开发团队应评审后选择等价方案。

### 3.4 一个最小数据契约示意

**P建议，非最终API Schema；示例值均为假设。** 保留原文GateEvidence字段语义；`observations`等封装字段用于说明缺失的协议维度，不声称原文已定义。

  "targets": ["machine-A", "machine-B"],
  "target_hash": "digest-of-frozen-selection",
  "required_path_coverage": ["nic-A:1 -> nic-B:1"],
  "test_profile": "approved-profile@version",

### 3.5 G5的深层建模结论

**D：必须区分“可以开始测”与“负载下已经被证明合格”。** NP-6的能力／基线是准入依据；本次负载窗口中的计数和LL判定是验收依据。若把二者都实现成一个网络健康布尔值，容易出现循环依赖或用旧窗口替代新试验。

**P建议的执行组织：** 先固定测试计划与观察要求；观察覆盖对应打流窗口；窗口资料完整后再评估L5；最后按所需检查和覆盖汇总G5。L1～L4是否逐层串行、无关路径能否继续、拥塞场景如何形成，保留Q1/Q3，不擅自认定。

| 证明层 | 能证明什么 | 不能顺带证明什么 |
|---|---|---|
| G2 | 实际接线与期望端口对一致 | IP配置、RDMA及性能正常 |
| G4 | 指定版本配置已应用并验证 | 真实业务路径在负载下合格 |
| G5 L1 | 所需端口的链路／速率／DOM检查结果 | IP或RDMA可达 |
| G5 L2 | 已测NIC对的IP可达性 | 未测对、RDMA流量类和无损行为 |
| G5 L3 | 对应RDMA写读与无损条件 | 多流热点／全路径和NCCL性能 |
| G5 L4 | 指定负载矩阵与热点的表现 | 长窗口拥塞规则已充分验证 |
| G5 L5 | 所需能力和窗口中的无损交叉判定 | 覆盖之外的未来任务仍可使用 |
| G6 | 指定通信组、档位与基线的NCCL评审 | 项目清理／撤权／客户签署已完成 |

**K：三源一致性核对**分别处理意图、配置态和硬件计数；无拥塞时计数不增长可以正常。**K：LL-03**需要完整3600s窗口、ECN恒零以及同窗口拥塞证据；仅ECN=0不能判异常，30s未观测异常也不能判完整验证通过。

**K：七类LL规则保持原义：** LL-01持续暂停；LL-02暂停风暴／死锁；LL-03 ECN恒不标记；LL-04标记过激；LL-05意图与设备不一致；LL-06无损队列丢包；LL-07 ECN/PFC余量不足。**P：** 规则结果先保留逐项再由策略聚合；LL告警级别、健康分和Gate结论不能混用。详细默认阈值沿用附件§7，本文件不另建第二份可漂移的阈值表。

### 3.6 现场名词在程序里究竟对应什么

下面沿用附件§1.1～1.2的语义，避免开发者凭设备名称猜业务。角色全称：DL＝交付组长，NE＝网络工程师，NH＝网络负责人，DE＝交付工程师。

| 原词 | 对开发的含义 | 不能替代它的值 |
|---|---|---|
| BOM／型号／商定基线 | 分别提供期望设备与连接、独立机型拓扑、批准的配置与性能判据；均需版本引用 | 待验证设备本次返回的数据 |
| Machine／Component／PhysicalPort | 整机、部件、物理端口的稳定身份层级；换件和关系变化可追溯 | OS接口名、BDF排序、列表行号 |
| GPU-NIC亲和／PCIe拓扑 | 主机内部的关联与链路能力，供映射、调度和解释性能使用 | 机器之间的外部接线关系 |
| rail | 批准网络方案中的分组属性，供配对与配置消费 | 开发根据网卡序号或交换机名称猜出的分组 |
| LLDP | 本端实际观察到的对端邻居；主机和交换机分别采集 | BOM期望、FDB或ARP单独形成的推断 |
| DOM／DDM | 光模块遥测；主机和交换机是不同观测来源 | 采集不到时填入的零值 |
| PFC／ECN／CNP | 分别是按优先级暂停、拥塞标记、RoCEv2拥塞通知；程序处理其配置、能力、计数和窗口 | 一个统一的“网络正常”布尔值 |
| Golden／IN_SYNC | intended与running经过复采比对的结果 | 命令退出码0、ZTP完成 |
| N-S／NP／G／Step／L／S／LL／SC／T | 依次是网络阶段标签、前置断言、门禁、G2步骤、G5层级、NCCL步骤、无损规则、NCCL场景、故障分类 | 互相替换的阶段序号 |

**物理动作的边界：** 接线、换卡、换光模块由现场人员执行；软件记录处理对象与新旧身份，再发起验证。人员点击“已处理”不能生产测试PASS。平台负责采集、配置、负载测试、证据判断与可追溯回执。

**后续流程卡的标注约定：** 业务输入、流程和完成语义以所列附件来源为K依据；冻结上下文和重新核对依赖的要求为D约束；动作幂等键、租约／fencing、结果不明先对账、事务组织与计划对象化均为P建议。卡中明确列出的Q仍未解决。该约定不把实现建议转换成原文要求。

## 4. 除了作者判断，如何证明文档正确

**不存在一种工具能单独证明这份需求在真实现场完全正确。** 必须区分以下证据的能力边界，并让不同责任方提供可重复核验的输入。

| 证据层 | 谁／什么提供独立约束 | 能证明的内容 | 不能证明的内容 |
|---|---|---|---|
| 来源与追溯 | 固定原附件摘要；每个流程／约束指向来源；评审记录 | 表达是否可追溯、是否偷加需求、哪些是建议／待决策 | 原附件本身的事实必然正确 |
| 结构与引用检查 | XML／JSON解析器、依赖图检查、消费者引用检查 | draw.io可解析、引用存在、正常前向依赖无环、产物有归属 | 阈值和物理方案符合现场 |
| 反例与边界检查 | 独立列出的输入及预期结果；反例复现记录 | 对选定约束，错误放行会被拒绝；边界不被漏掉 | 全部执行路径和全部现实故障均正确 |
| 并发／恢复模型 | 有限状态枚举；必要时TLA+／TLC等模型检查 | 在明确抽象和边界内，不存在特定错误状态或死锁 | 模型遗漏的状态以及生产实现必然正确 |
| 适配器契约 | 厂商原始命令输出、独立golden-file、故障注入与版本矩阵 | 解析、计数器语义、unknown路径与真实样本一致 | 现场链路在实际规模下满足性能 |
| 现场PoC | NE／NH提供网络期望；硬件厂商基线；真实拓扑与打流记录；DL确认 | 软件结论与实物、配置、负载结果是否一致 | 未测试型号、规模、版本自动适用 |
| 开发验收与交付签署 | 需求负责人、实现负责人、测试负责人分别核验 | 实现是否满足已批准规格，哪些决策已关闭 | 未签署项被默认为已接受 |

**本次实际执行的是“结构检查＋有限契约反例＋有限状态模型”**，不是生产系统测试、第三方认证或现场PoC。检查程序与文档仍来自同一交付，不能算独立专家已经签字；它提供可被他人复跑和反驳的证据。

方法参考只支撑验证方法，不赋予本文新增业务规则权威：

- [NASA SWE-052 双向追溯](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695427/SWE-052%2B-%2BBidirectional%2BTraceability)：用于连接需求、设计和验证证据；这里不宣称keel适用NASA项目分级。
- [JSON Schema 官方说明](https://json-schema.org/docs)：可定义结构、类型与约束；结构有效不等于现场事实正确。本次结构校验采用标准库明确断言，不声称执行了完整生产API Schema验证。
- [TLA+ Tools](https://lamport.azurewebsites.net/tla/tools.html)：TLC可检查可执行规格的安全性与活性；[有限实例说明](https://lamport.azurewebsites.net/tla/model-popup.html)解释模型检查的范围。本次使用透明的小型Python枚举器，未运行TLC，也不声称形式化完备证明。

**对本文自身的接受标准：** 每个流程有明确生产／消费关系；每个未决项有影响范围；K/D/P/Q可辨；主图不制造G2↔G3循环；G4不遗漏；G5不伪设串行策略；恢复不绕过无关条件；报告中的验证结果必须来自实际执行，未执行验证明确标记。
